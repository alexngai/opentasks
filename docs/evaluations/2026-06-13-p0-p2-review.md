## Review 1 — Correctness & Concurrency (code-reviewer): APPROVE, 0 Critical/High
This is an important nuance for the atomicity claim. The IPC handler `await`s each request before processing the next line *on the same socket*, but **multiple sockets (connections) can have their `data` handlers interleave at `await` points**. Two different agents connect via two sockets; each calls `tools.task` with a claim. Their handler invocations CAN interleave at `await` boundaries.

This is exactly why the claim decision must be atomic *within a single synchronous SQLite UPDATE* — and it is. The interleaving happens around the `await store.getNode()` existence check and around `await flushManager.flush()`, but the actual `claimNode` UPDATE is synchronous and atomic. So even with concurrent connections, two claimants cannot both win. The empirical test confirmed this. The atomicity claim holds precisely because it does NOT rely on the daemon serializing whole requests — it relies on the single synchronous conditional UPDATE.

### Verification of the central claim

The claim is: *"a single conditional SQLite UPDATE is atomic because better-sqlite3 is synchronous and the daemon is single-threaded, so there is no await-gap between the guard check and the write."*

This is **correct**, and importantly it is correct for a stronger reason than "the daemon serializes requests" — it does **not**. In `src/daemon/ipc.ts:206-240`, each socket's `data` handler `await`s `handleRequest` before processing the next line *on that socket*, but **different connections interleave freely at every `await`**. Two agents on two sockets calling `tools.task({claim})` will interleave around `await store.getNode()` (coordination.ts:339) and around `await flushManager.flush()` (tools.ts:204).

The design survives this because the actual claim decision is a **single synchronous `UPDATE ... WHERE <guard>`** inside `this.db.transaction()` (sqlite.ts:332-373). better-sqlite3 executes it to completion with no yield point, so the guard evaluation and the write are indivisible. The guard `(claimed_by IS NULL OR claimed_by=@claimant OR lock_until IS NULL OR lock_until <= @now)` is evaluated by SQLite against the row at write time, not against a JS snapshot read earlier. There is no TOCTOU gap. I confirmed empirically (two concurrent claimants → exactly one `changes=1`, holder is the winner).

Specific sub-verifications, all passing:
- **Fence increment** `claim_fence = COALESCE(claim_fence,0)+1` correctly handles legacy NULL rows (→ 1) and increments monotonically. Confirmed empirically.
- **Stale fence release/renew** rejected: `releaseNode`/`renewNode` add `AND claim_fence = @fence`; a stale fence yields `changes=0` → `ok:false`. Confirmed.
- **ISO `lock_until <= @now` string comparison** is correct: `Date.prototype.toISOString()` always emits fixed-width UTC `...Z`, so lexicographic order equals chronological order. All timestamps in this code path go through `toISOString()`, so there is no mixed-offset hazard.
- **Non-task / archived / missing node** correctly rejected by `type = 'task' AND (archived IS NULL OR archived = 0)`. Confirmed (`changes=0`).
- **`markDirty` inside the transaction** is correct — the dirty mark and the claim commit atomically together; a crash can't leave a claim un-flushed-but-committed-as-clean.
- **F2 deadlock check**: A durable claim awaiting `flushManager.flush()` while a sync holds the flush paused does **not** hang — `flush()` returns immediately when `isPaused` (flush.ts:130-133). The node stays in `dirtyNodes` and is re-scheduled on `resume()` (flush.ts:142-149). Confirmed empirically. The node also persists in SQLite regardless (the claim already committed), so a crash before resume still recovers the claim on the next JSONL flush/reload cycle.
- **Auto-sync never pulls**: `startAutoSync` (git-graph-syncer.ts:387-411) only runs `commitIfDirty` and `push`. All pulls are confined to the IPC `sync.now`/`sync.pull` paths, both routed through `coordinated()` (sync.ts:118-139). The F2 race surface is correctly confined.
- **SQL injection**: All new SQL uses bound parameters. The dynamic `${guard}` / `${fenceGuard}` template pieces are **constant string literals** selected by a boolean (`opts.force`, `opts?.fence != null`) — never user data. Safe.

### Issues

**[MEDIUM] `claimNext` carries a real but acceptable TOCTOU window — only the post-filter is authoritative**
File: `src/graph/store.ts:382-398`
Issue: `claimNext` reads `getReady()` then iterates, pre-filtering with `node.lock_until > nowMs` in JS before calling `claimManager.claim()`. The pre-filter is a stale JS read and is racy — but this is *safe* because `claimManager.claim()` → `claimNode` is the authority and a lost race just yields `result.success=false` and moves to the next candidate. The pre-filter is purely an optimization to skip an obviously-live lease. Two concerns worth noting: (1) the comment says "claim the first one that isn't under a live lease" which slightly overstates the guarantee — the JS check can be stale, the SQL check is what actually protects. (2) If two `claimNext` callers race over the same ready set, they correctly diverge (one wins each task), but neither pre-filter prevents both from *attempting* the same first task — acceptable, just a wasted UPDATE. No correctness bug.
Fix: Tighten the comment to "...claims candidates in order; the atomic UPDATE is the authority, the lease pre-check is a best-effort skip." Optionally push the readiness+unclaimed filter into a single SQL `claimNextReady` statement (`UPDATE ... WHERE id = (SELECT id FROM ready_tasks WHERE <unclaimed-or-expired> LIMIT 1)`) to make claimNext itself a single atomic statement and eliminate the N round-trips. Not required for correctness.

**[MEDIUM] `claimNode` failure outcome cannot distinguish "held by someone else" from "not a task / archived"**
File: `src/storage/sqlite.ts:345-357`
Issue: When the UPDATE matches zero rows, the code runs `selectCurrent` and reports `claimed_by`. For a node that exists but is archived or non-task (and unclaimed), `claimed_by` is NULL, so the caller (coordination.ts:346-355) reports `Cannot claim node: <id>` with no `existingClaim`. That is fine. But for a node that is **archived yet still has a stale `claimed_by` set** (e.g. archived while claimed), the failure path will report `Node is claimed by X` even though the real reason the claim failed is that it's archived — a misleading error. Functionally the claim is correctly denied; only the diagnostic is wrong.
Fix: In the zero-changes branch, re-select `type` and `archived` too and prefer a precise reason: if `type != 'task'` → "not a task", if archived → "archived", else fall through to the holder report. Low blast radius; purely improves error messaging.

**[MEDIUM] Lease reaper sweeps every location's claims through a single `activeProviderStore`, but in multi-location mode the reaper isn't wired at all**
File: `src/daemon/lifecycle.ts:752-763` (single-location only)
Issue: The 60s lease reaper (`claimSweepIntervalHandle`) is installed only in `createSingleLocationDaemon`. The multi-location daemon (`createMultiLocationDaemon`, lines 1006+) has no equivalent reaper, so expired claims in worktree locations are never actively cleared — they remain reclaimable via steal-on-expiry (so no correctness loss for claiming), but the stale `claimed_by`/`lock_until` fields are never cleaned up and never flushed to notify watchers. The `sweepExpiredClaims` plumbing exists on every store, so this is an omission, not a design limit.
Fix: Factor the reaper into a helper and start one per `LocationState` in `initLocation` (multi-location), mirroring the per-location reconciliation intervals already there (lines 1136-1160), and clear them in the multi-location teardown.

**[LOW] Reaper swallows the dirty-mark race window between sweep and flush is fine, but `markDirty` + `schedule` on the flush manager is *not* durable**
File: `src/daemon/lifecycle.ts:757-761`
Issue: After a sweep clears claims, the reaper does `fm.markDirty(id)` + `fm.schedule()` (debounced), not `await fm.flush()`. So a reaper-cleared claim is only persisted to JSONL after the debounce (up to 30s) — and if the daemon crashes in that window, the SQLite clear is lost too (since SQLite is a cache rebuilt from JSONL on next start). Net effect: the claim "un-expires" on restart and stays stuck until the next reaper tick. Steal-on-expiry still lets a new claimant take it, so it's self-healing, but the cleared state isn't durable. This is a reasonable tradeoff (reaper output is advisory) but worth a comment or an `await fm.flush()` if durability of the cleared state matters.
Fix: Either document the non-durability explicitly, or `await fm.flush()` after the markDirty loop (consistent with the durable tier used for actual claims in tools.ts).

**[LOW] `coordinated()` resumes the flush in `finally` even if `reloadStore()` left SQLite mid-rebuild**
File: `src/daemon/methods/sync.ts:126-138`
Issue: The order is correct (drain → pause → run git → reload-if-changed → resume). `reloadStore` errors are swallowed (lines 128-134) and the flush resumes regardless. If `store.reload()` partially rebuilt SQLite from the merged JSONL and then threw, the resumed debounced flush will write the partial SQLite state back over the good merged JSONL — a potential data-loss-on-reload-failure. In practice `store.reload()` (store.ts:404+) does upserts and is fairly robust, and reload failure is rare, but the swallow-and-resume pattern means a half-applied reload becomes the new source of truth on the next flush.
Fix: On `reloadStore` failure, consider not resuming the debounced flush automatically (or marking the store unhealthy / forcing a fresh reload) so a corrupted SQLite state can't be flushed back over the canonical JSONL. At minimum, log the swallowed error rather than discarding it.

**[LOW] `releaseNode` is not exercised through the durable flush tier with a fence, and `release` always reports `success:true`**
File: `src/tools/task.ts:306-318`, `src/daemon/methods/tools.ts:186-196`
Issue: `handleRelease` returns `{ success: true, data: { released } }` even when `released === false` (release rejected by fence/holder guard). The caller in tools.ts then marks dirty + durable-flushes based on `d.type === 'release'` regardless of whether anything actually changed — so a no-op release (e.g. stale fence) still triggers a durable flush of an unchanged node. Harmless (flush of a clean node is a no-op at the JSONL layer) but the `success:true` on a failed release is a slightly misleading API contract; a caller can't tell from `success` whether the release took effect without inspecting `data.released`.
Fix: Keep `success:true` (it's a valid "operation completed" signal) but document that `data.released` is the authoritative result, or only mark dirty/flush when `released === true`.

**[LOW] Duplicated `updateableFields` list and dirty-mark SQL across async and sync code paths**
File: `src/storage/sqlite.ts:255-283` vs `805-833`, and `markNodeDirty` (314-318) vs `markDirtySync` (895-901) vs `markDirty` (946-952)
Issue: The `updateableFields` array is duplicated between `updateNode` and `updateNodeSync` and they have drifted — the async `updateNode` (line 280) includes `claim_fence` in its updateable list, but the sync `updateNodeSync` (lines 805-833) does **not** include `claim_fence`. So a `claim_fence` update routed through a transaction (`runInTransaction` → `updateNodeSync`) would be silently dropped. Today the claim path uses the dedicated `claimNode`/`renewNode` UPDATEs (not `updateNodeSync`), so this isn't hit — but it's a latent footgun if anyone updates `claim_fence` via the transaction API. There are also three near-identical dirty-mark implementations.
Fix: Extract a single shared `UPDATEABLE_FIELDS` constant used by both paths, and add `claim_fence` to the sync path for parity. Collapse the three dirty-mark helpers into one.

### Positive Observations

- Durable vs debounced flush tiering (tools.ts:170-208) correctly classifies claims/leases/terminal transitions as crash-critical while keeping ordinary edits debounced.
- Steal-on-expiry plus the reaper are complementary, not redundant — the system is correct (reclaimable) even if the reaper never runs.

# OpenTasks `hardening` Branch — Architecture & Integration Coherence Review

## Summary

The atomic-claiming feature is genuinely well-built at its core: the SQLite conditional-UPDATE design (sqlite.ts:320-472) is race-free, and the fence/lease/reaper machinery is threaded coherently from storage all the way to the MCP/CLI/client surface and into swarm-dispatch. The substrate **is** now a real coordination layer for *native* tasks — the central question of the original eval closes affirmatively, but with a narrower scope than the framing implies. The dominant coherence risk is **terminal-state semantics**: `failed`/`abandoned` were added as first-class statuses but the graph's "active blocker" and "ready" logic, the context-summary breadcrumbs, and the MAP round-trip were never taught about them, so the new states leak in three places. The second-order risk is **honesty drift in STATUS.md** around the native-only claiming boundary and "lossless" MAP round-trip.

## The 5 strongest architectural observations

**1. The claiming core is correct and the wiring is complete and consistent end-to-end.**
The atomicity argument holds: `claimNode` runs the guard + write + fence-bump + read-back inside one synchronous `better-sqlite3` transaction (sqlite.ts:332-373), so there is no await-gap TOCTOU. The guard clause (sqlite.ts:329-331) correctly admits free / self-owned / expired claims; `force` drops the guard. Release (sqlite.ts:376-395) and renew (sqlite.ts:397-444) are fence-guarded conditional UPDATEs; `sweepExpiredClaims` re-checks expiry per-row in the UPDATE WHERE (sqlite.ts:454-458) so it can't clobber a freshly re-claimed task. The shape threads cleanly: `ClaimOutcome` (interface.ts:85-96) → `ClaimResult`/`ClaimInfo` (coordination.ts:115-170) → `TaskClaimData`/`TaskReleaseData` (types.ts:485-512) → MCP tools (server.ts:357-428) → CLI subcommands (cli.ts:746-822) → swarm-dispatch. The six `LOCAL_ID_PATTERN` definitions are all byte-identical (`/^[ctfex]-[a-z0-9]+$/`), and `src/index.ts` re-exports the store/types. This is the high-water mark of the branch.

**2. Terminal states are not wired into "active blocker" / "ready" logic — `failed`/`abandoned` tasks block their dependents forever.** (Biggest coherence defect.)
`failed` and `abandoned` are terminal but are not `closed`. Both places that decide whether a blocker is "still active" test only against `closed`:
- `ready_tasks` view: `blocker.status != 'closed'` (sqlite-schema.ts:135)
- query engine: `isActiveNode = !node.archived && node.status !== 'closed'` (query.ts:154)

So if task B blocks task A and B is marked `failed`/`abandoned`, A never becomes ready and B still shows up as an "active blocker." Semantically a failed/abandoned blocker should usually *stop* blocking (the work it gated isn't coming). At minimum this is inconsistent with the new state model the branch just introduced. The fix is one predicate (`status NOT IN ('closed','failed','abandoned')`) in two places, but it needs a deliberate decision — see the tradeoff below.

**3. Context-summary silently drops or miscategorizes terminal failures.**
The breadcrumb builder (query.ts:570-649) was not updated for the new states:
- Sibling classification (query.ts:578-590): a `failed`/`abandoned` sibling is neither `closed` nor `blocked`, so it falls into the `else` branch and is reported as an **active task** — actively misleading.
- The broad queries fetch `status:'closed'` for recentlyCompleted (query.ts:603-605) and `status:['open','in_progress']` for active (query.ts:620-622). `failed`/`abandoned` tasks match neither, so outside the sibling path they vanish from session continuity entirely.

This is the same root gap as #2: the status taxonomy widened, the consumers didn't.

**4. The claim SQL conflates `assignee` with `claimed_by`, and release doesn't restore it.**
`claimNode` writes `assignee = @claimant` alongside the claim fields (sqlite.ts:335). But `assignee` is an independent user-facing field with its own dedicated path (`taskAssign` → native.ts:710) and its own MCP surface. Consequences:
- Claiming a task silently reassigns it, overwriting any human-set assignee.
- `releaseNode` only nulls `claimed_by/claimed_at/lock_until` (sqlite.ts:385) — it leaves `assignee` pinned to the last claimant. After release the task reads as "assigned to agent-X" though no one holds it.

Two ownership models (soft `assignee`, hard `claimed_by`) are being written through one column-set without a documented reconciliation rule. STATUS.md:66 even distinguishes them ("Plain assignee … for exclusive ownership use atomic claim"), but the code couples them.

**5. The fence/agentId opaque-token contract with swarm-dispatch is sound, and it closes the loop the original eval flagged as broken.**
The original break (HARDENING-PLAN.md:40) was that the adapter called a nonexistent `unassign` op. The branch fixes the root cause: opentasks now exposes real `claim/release/renew` with fences, and the adapter (`opentasks.ts`) wraps `{agentId, fence}` into the opaque `FenceToken` (types.ts:41) precisely because `renewClaim(taskId, fence)` (store.ts:128) carries no claimant. This is the *right* use of an opaque token — swarm-dispatch's `FenceToken = string | number | object` was designed for exactly this, and the orchestrator stores it verbatim (types.ts:457). The contract genuinely closes: claim returns `{agentId, fence}`, renew/release thread both back through, and a lost claim surfaces as `{ok:false}` (opentasks.ts:112) which the orchestrator treats as stolen. This is coherent and not fragile — the only sharp edge is that the adapter's `release()` is fire-and-forget (opentasks.ts:95-100, no return-value check), so a fenced-reject on release is swallowed; minor, since release races are benign.

## The 3 biggest coherence risks

**Risk A — Terminal-state taxonomy is half-integrated (observations #2 + #3).**
The branch added `failed`/`abandoned` to the *write* side (TaskAction, native statusMap, MAP mapping, MCP enum) thoroughly, but not to the *read/query* side (ready view, active-blocker test, context summary). A status model is only coherent if producers and consumers share it. Right now an agent can `fail` a task and (a) wedge everything downstream of it and (b) make it disappear from the session breadcrumbs. This is the single highest-value fix.

**Risk B — STATUS.md overstates two things the code doesn't deliver.**
- *Native-only claiming is undocumented.* `taskClaim/taskRelease/taskRenew` reject any non-native provider with `NOT_SUPPORTED` (provider-store.ts:1320-1356), but STATUS.md:67 presents "Atomic claim / claimNext ✅" with no caveat. For a system whose thesis is cross-provider multi-agent coordination, "you can only atomically claim *local* tasks, not beads/MAP/sudocode tasks" is a load-bearing limitation that belongs in the as-built doc with a 🟡, not omitted.
- *"Lossless MAP round-trip" is false for `abandoned`.* STATUS.md:70 claims "lossless MAP completed/failed round-trip." But `abandoned → MAP failed` (map.ts:171, map-event-bridge.ts:222) and inbound MAP `failed → failed` (map.ts:155) — so an `abandoned` task that round-trips through MAP comes back as `failed`. It's lossless for `completed`/`failed` only; `abandoned` is lossy. The doc's own parenthetical accidentally tells the truth ("completed/failed") while the adjective ("lossless") overclaims.

**Risk C — Duplicated hardcoded action lists will drift (maintainability, not yet a bug).**
The `TaskAction` set is re-encoded in at least five places that must stay in sync by hand: the task tool's `validActions` array (task.ts:154), the `TaskParams.transition.action` union (types.ts:338), the MCP `z.enum` (server.ts:153), native's `statusMap` (native.ts:639-647), and the canonical `TaskAction` type (TaskManageable.ts:26). The branch just exercised this fault line — adding `fail`/`abandon` required touching all five, and the providers diverged *correctly* (beads/sudocode `Partial`, claude-tasks already `Partial`) but only because a human remembered each site. The right consolidation: derive the tool-level validator and the MCP enum from the exported `TaskAction` type (e.g. a single `const TASK_ACTIONS = [...] as const` that both the `z.enum` and the runtime array consume), so the type is the single source of truth. Low effort, removes a recurring drift class.

## Verdict: Is the substrate now genuinely a coordination layer?

**Yes — for native tasks, with two caveats that must be addressed before the claim is fully honest.**

The hard part is done and done correctly: there is real compare-and-swap (sqlite.ts:332-373), real leases with a working reaper (lifecycle.ts, 60s sweep), real fencing that rejects stale holders, and a real consumer (swarm-dispatch) that drives it through a closed contract. The original eval's central failure — "two agents claiming, second silently wins; adapter calls a nonexistent op" — is genuinely fixed. This is no longer a graph that *pretends* to coordinate; it coordinates.

The two caveats keep it from being a coordination layer in the *federated* sense the project's framing promises: (1) coordination stops at the native provider boundary — you cannot atomically claim a beads or MAP task, and that limit is undocumented; and (2) the terminal-state model is internally inconsistent, so the very "failed/abandoned" outcomes that a coordinator needs to reason about (to stop blocking, to retire work) leak into the wrong query results. Neither undermines the foundation — both are localized, well-scoped fixes — but until terminal states are integrated into the read path and STATUS.md is corrected, the substrate is a *solid native-task coordination layer wearing a federated-coordination label*.

### Headline Claim Judgments

**"16 concurrent claimants → exactly one winner" — ADEQUATELY TESTED with a structural caveat**

The test (`coordination.test.ts` lines 197–216 and `claim-wiring.test.ts` lines 103–108) fires 16 `Promise.all` calls and asserts exactly one winner. The claim of atomicity is structurally sound: `claimNode` in `sqlite.ts` is a synchronous `better-sqlite3` transaction with a conditional UPDATE — there is genuinely no `await` gap between the guard and the write, so no two callers can both see the node as unclaimed and both win. The test proves the invariant holds in practice. However, the contention is **trivially serialized**: Node.js is single-threaded, so `Promise.all` of 16 synchronous-SQLite calls resolves them one by one in microtask order. This is not a weakness in the implementation (which is correct by construction), but it does mean the test cannot distinguish "atomic CAS" from "serial execution" — the test would pass even on the old read-modify-write code if all 16 awaits happened to serialize by luck. The meaningful guarantee comes from the implementation design (single conditional UPDATE), which the test confirms does not produce double-claims. The HARDENING-PLAN is honest about this: it notes "same guarantee; bump if a CI scale test is wanted."

**Fence rejection (stale fence, post-steal) — ADEQUATELY TESTED**

Stale-fence rejection on `release` and `renew`, and post-steal fence invalidation, are each covered by dedicated tests at both the storage layer (`coordination.test.ts`) and the tool layer (`claim-wiring.test.ts`). The SQL guard (`AND claim_fence = @fence`) is confirmed in the implementation. Tests are mechanically tight.

**Lease steal after expiry (via injected `now`) — ADEQUATELY TESTED**

The `now` injection path is clean: `claimNode` accepts `opts.now` and uses it for both the guard comparison and the `lock_until` calculation. Tests confirm the fence increments on steal and the original holder is displaced.

**`sweepExpiredClaims` clobber-safety — ADEQUATELY TESTED for the common case, gap for interleaved re-claim**

The per-row re-check guard in `sweepExpiredClaims` (`UPDATE … WHERE id = @id AND lock_until <= @now`) is correct and the implementation is inside a single SQLite transaction. The test confirms cleared IDs are returned and live claims are left alone. What is not tested: a scenario where a task's lease expired, the SELECT captures it, then between SELECT and UPDATE a new agent re-claims it (bumping `lock_until` into the future) — the guard should protect it. This is a meaningful edge case for the reaper but given the single-threaded SQLite transaction the guard is structurally sound; the gap is a test coverage gap, not an implementation gap.

**F2 sync coordination — ADEQUATE AS A DETERMINISTIC SUBSTITUTE, with a residual risk acknowledged**

The author's choice to test call ordering deterministically (mock syncer + mock flushManager, assert `calls === ['flush','pause','commit','pull','reload','resume']`) rather than a "100-iteration timing test" is defensible. A timing test on a single-machine test runner has high variance and would not prove anything the ordering test doesn't. The deterministic test directly asserts the sequence that eliminates the race. The real-daemon e2e (`e2e-git-sync.test.ts`, 41 tests) exercises the coordinated path with actual git. **What a stronger test would add:** a test that fires a `store.update()` concurrently with `sync.pull` and asserts the update is not lost — i.e., the write-during-sync residual window (documented in SYNC.md "Write-during-sync (F2 residual)"). This is the one scenario the deterministic test cannot prove because it is not covered by ordering assertions alone. The HARDENING-PLAN honestly labels this a "residual race" and defers the full fix to multi-machine causality work.

**Durability tiers — PARTIAL (unit-level only)**

The `tools.test.ts` durability tests verify that `flushedBatches` contains the expected node ID after the RPC returns. This proves the flush call was made synchronously before the IPC response. The gap is that `flushManager` in the test is a real `DaemonFlushManager` but the write function is a no-op (`async (ids) => { flushedBatches.push(ids); }`) — it does not write to SQLite or disk. A kill-restart test (start daemon, claim, `kill -9`, restart, assert claim survives) would close this gap. The HARDENING-PLAN explicitly notes this: "Unit-level; a full kill-restart e2e could be added." Given the flush path is the same one exercised by the full e2e git sync tests and the implementation is straightforward, this is a low-risk gap.

### Gaps (ranked by risk)

1. **STATUS.md stale after P2** — `docs/STATUS.md` "Flush ↔ git-pull serialization" row still reads `🟡 Not yet serialized` even though P2 (commit `f2ed408`) fixed it. An evaluator reading STATUS.md sees a regression signal that does not reflect reality. Risk: **medium** (doc credibility). Suggestion: update the row to `✅` with a note pointing to `sync-coordination.test.ts` and `e2e-git-sync`.

2. **MAP `failed↔failed` round-trip has no dedicated unit test** — `map-connector.test.ts` contains zero references to `failed` or `abandoned`. The inbound mapping (`mapStatusToOpenTasks`) changed `'failed' → 'failed'` (was `'closed'`), but no test verifies that a MAP task arriving with `status: 'failed'` is stored as `failed` in OpenTasks and then emitted back as `failed` when synced outbound. The two mapping functions (`mapStatusToOpenTasks` and `mapStatusToMAP`) are individually readable but their composition through the provider is untested. Risk: **medium** (the claim "lossless MAP completed/failed round-trip" is accepted criteria for P1 but is backed only by reading the code, not by executing it). Suggestion: add a `map-connector.test.ts` case: mock a MAP client that returns a task with `status: 'failed'`, assert the resulting ProviderNode has `status: 'failed'`, and assert the reverse mapping in a `getTask` → re-emit path.

3. **`claimNext` tag and priority filtering is wired but untested** — The `ClaimNextOptions` interface declares `tags?: string[]` and `priority` fields. `provider-store.ts` passes them through to `getReady` via `nativeFilter.tags`. `store.ts:claimNext` calls `storage.getReady()` but does NOT pass any filter — it ignores `options.tags` and `options.priority` entirely (confirmed by reading lines 382–398 of `store.ts`). This means agents using `claimNext({ tags: ['urgent'] })` get the full ready set, not a filtered one. No test exercises this path, so neither the bug nor the limitation is caught. Risk: **high** (behavior diverges from interface contract; agents relying on tag-scoped claiming will silently get unscoped results). Suggestion: add a test: create tasks with and without a given tag, call `claimNext({ agentId, tags: ['urgent'] })`, verify only the tagged task is claimed. Then fix the `claimNext` implementation to pass the filter to `storage.getReady`.

4. **Daemon lease reaper timer — integration-level behavior untested** — The 60s `setInterval` in `lifecycle.ts` (lines 744–760) calls `providerStore.sweepExpiredClaims()` and marks dirty nodes. The storage primitive is tested; the interval wiring is not. There is no test that starts a real daemon, creates a claimed task, advances time or uses a short interval, and asserts the claim is cleared. Risk: **low-medium** (the wiring is three lines and visually correct; but startup/shutdown clearInterval paths are untested, and the `markDirty` + `schedule` call after the sweep is only in the daemon code, not covered by unit tests). Suggestion: add a daemon integration test with a very short sweep interval and an expired claim.

5. **Write-during-sync residual race untested** — Documented in SYNC.md. A write arriving during the `pause` window can be overwritten by the post-pull reload. No test covers this. Risk: **low** (small window, honestly documented as a known limitation requiring multi-machine causality work to fully fix). No suggestion beyond what HARDENING-PLAN already says.

6. **CLI `claim`/`release`/`renew` tested only for argument validation, not daemon interaction** — `cli.test.ts` additions confirm the commands appear in `help` output and exit-1 with usage on missing args. There is no test that runs `opentasks claim <id> --agent foo` against a live daemon and verifies the claim is recorded. Risk: **low** (the dispatch path from CLI → client → daemon → tool is exercised by other integration tests; the CLI additions are thin wrappers). Consistent with what the HARDENING-PLAN says: "daemon-free arg-validation tests."

7. **Multi-agent dead-agent recovery e2e** — No test simulates a swarm scenario where one agent dies, its lease expires, the reaper clears it, and a second agent successfully claims the task. This is the headline use case for leases. Risk: **low** for correctness (each primitive is tested in isolation and the composition is straightforward), high for confidence in the scenario end-to-end. Flagged as P5 ("real-daemon e2e") in HARDENING-PLAN.

### De-flaking Assessment

The P0 timeout and gating changes are legitimate:

- **`e2e-git-sync` and `cli.test` timeout raised to 30s**: These tests spawn real `git` subprocesses and child processes. The default 5s timeout was too tight under parallel load. Raising to 30s with a comment referencing HARDENING-PLAN P0 is appropriate; it does not hide correctness problems, only accommodates subprocess latency.
- **`vitest.config.ts` hookTimeout raised from 10s to 30s for the default suite**: `hookTimeout` governs `beforeEach`/`afterEach`, not the test body. Raising it prevents false failures in git-spawning setup/teardown. The 5s `testTimeout` for the fast lane is unchanged, so unit-test regressions would still surface promptly.
- **Chokidar watcher tests gated behind `RUN_SLOW_TESTS`**: Three `describe.skipIf(!RUN_SLOW_TESTS)` blocks are added to `sessionlog-watcher.test.ts`. The root cause was filesystem-event tests (which require chokidar polling + `awaitWriteFinish`, inherently ~500ms minimum) being in the fast lane. Gating them is the correct fix, consistent with the existing `filesystem integration` precedent in the same file. They remain reachable via `npm run test:slow`. The HARDENING-PLAN records this decision explicitly. No real bugs are hidden.

The 29 skipped tests in the default suite are all chokidar/filesystem-event cases — confirmed by the `describe.skipIf(!RUN_SLOW_TESTS)` pattern. They are not skipped due to flakiness in the feature under test.
